# 为什么差这么多：环境排查与证据分级

**当前证据更支持“模型对这套Feishu 消息场景的泛化与概率使用方式不匹配”，不支持把大幅低分归因于这台Mac。也没有证据把Jev的优势具体归因于更多预训练知识。** 此分析不改变冻结数据、标签或正式成绩。

## 1. 已检查的环境因素

| 检查项 | 证据 | 能排除到什么程度 |
|---|---|---|
| 权重下载损坏或用错文件 | 完整SHA-256与该Hub revision的多语言权重一致 | 排除文件不完整、误加载其他权重 |
| 错用英文模型处理中文 | 元数据确认mmBERT多语言版本，直接加载、不经过自动路由 | 不是语言路由错选英文权重 |
| MPS导致数值异常 | 分层固定抽8例，每例两种提示，共16次CPU复查；16/16标签一致，返回概率最大差0.0 | 在API返回的四位小数精度下一致，降低MPS专有计算错误嫌疑 |
| 低精度量化导致退化 | CPU与原MPS路径均按FP32执行，没有GGUF/4-bit量化 | 本轮不是量化精度损失实验 |
| 上下文或问题被截断 | 全64例两种模式的state/instructions未截断；选项也均小于48-token限制 | 不能用默认上下文短解释本轮低分 |
| 请求失败、输出缺失 | 768次计时请求成功；双方结构化请求哈希匹配 | 不是把HTTP失败算成错误标签造成的差距 |
| 评分或接口误接 | 完整性测试、冻结标签检查、条件阈值测试、两种提示独立运行 | 已检查已知评分路径，不能证明任何实现绝无bug |

[CPU复查记录](../results/v1/environment_check.json)与[复查脚本](../diagnostics/environment_check.py)已公开。选样为每个排序后的family取轮换的第1至第8例，类别各2例，没有按模型错误挑样本。

**剩余边界：CPU和MPS共用同一份Python推理代码、PyTorch/Transformers版本和权重。** 这不是CUDA或另一套独立实现的复现，不能排除共享实现问题，也没有系统扫描所有依赖版本。之前遇到的editable包导入失败发生在推理前，修复导入路径后才记录成绩。

## 2. 最有依据的解释：基础模型的陌生任务泛化

Laya官方报告本身区分了基础版与专用微调版。在typed-decisions任务上，多语言基础版约0.342，专门微调版约0.766；两者不能混为同一能力。作者也明确把Laya定位为适合针对任务专门化的基础模型，并披露跨任务与校准限制。这与本轮Feishu 消息场景低分方向一致，但不是直接证明同一种原因。[Laya官方测试报告](https://github.com/NandhaKishorM/laya/blob/42626c348753fbb17572a813127df2278a1ec527/BENCHMARKS.md)

本仓库测试的是**未针对这些情境微调的多语言基础权重**。题目要求同时绑定目标消息、识别人、解析否定和取消、过滤其他群内容，再按新规则分类；它不是固定领域的简单关键词分类。把这些能力泛化差异作为主要解释是合理推断，尚非受控因果实验。

## 3. “懂中文”不等于“稳定遵守新工作流”

Laya多语言版基于mmBERT。其底座官方说明是双向、掩码语言建模预训练的多语言编码器，训练数据超过3万亿tokens。因此“Laya没有预训练/没知识”是不准确的。语言表征能力与对任意新规则进行条件判断，是不同能力；底座数据量不能直接转换成工作流准确率。[mmBERT模型卡](https://huggingface.co/jhu-clsp/mmBERT-base)

同时，不应从一个encoder的失败推断所有encoder都不行：领域数据、决策头训练、指令覆盖、负例构造和多语言后训练都可能影响结果，本轮未分别消融。

## 4. 概率校准和组合阈值也有影响，但不是全部原因

多语言checkpoint配置中的温度是1，分桶温度为空；上游也披露未拟合温度、存在过度自信问题。我们沿用冻结阈值，并未在评测标签上调参。因此four_noul结果同时反映模型概率质量与固定决策规则的适配程度。不同模型可能需要在**另一个开发集**上校准。[Laya模型说明](https://huggingface.co/convaiinnovations/laya)

但单choice也仅20/64，说明问题并不只来自四问组合。一般的正温度缩放不会改变choice的最大概率类别，也不会改变二分类概率位于0.5哪一侧；它能改善置信表达和拒答阈值，却不能自动修复大量语义判断错误。

## 5. 是否能说Jev的pretraining更强、知识更多？

**不能据此下结论。** TypeSafe公开描述了RLCD决策后训练、结构化输出和并行求值方向；本次查阅的一手资料没有给出可用于与Laya定量比较的完整底座、参数规模、预训练语料和算力配置。[TypeSafe训练说明](https://docs.typesafe.ai/introduction/machine-learning-primer)、[官方发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev)

而且，这64例主要测上下文、指代、状态和规则执行。答案需要的信息就在输入里，并非百科问答；即便优势与更好的语言预训练有关，也无法和后训练数据、决策目标、架构及提示适配分开。更稳妥的结论是：**当前Jev服务在这套冻结Feishu 消息场景上表现出更好的指令与上下文泛化。机制仍未知。**

Jev也不是无短板：官方列出了数字精度、日期、间接引用、长无关上下文等限制。本集没有覆盖所有这些能力；64/64不能当作通用满分。[Jev已知限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13)

## 6. 测试本身能解释多少

- 64例是AI辅助编写的合成情境，没有独立多标注者共识或隐藏测试集。部分例子较相似，明显的否定和转派措辞可能偏向某种指令模型。
- 规则明确、标签平衡，能定位错误；却不能估算真实团队消息分布下的错误率。
- 所有提示都事先固定，但设计参考过早期12例探索，不能称作真正盲测。
- 只比较这两个版本及配置，没有测Laya的中文领域微调版本、其他小分类器或Jev所有语言。
- CPU复查的16次请求是单列环境诊断，不并入原768次正式计时成绩。

因此，成绩图表达的是**某个固定任务、明确配置与协议下的实测差距**，不是“Laya全面不行”或“Jev拥有更多世界知识”。
